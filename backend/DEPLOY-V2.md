# CinemaHome API v2: подготовка к развёртыванию

Текущий статус: код и миграция проверены на отдельной MariaDB 10.11; на VPS не применялись. Android TV пока не подключён к v2. Публичные TV-функции не переключать до проверки потока целиком.

1. Сделать защищённый backup именно базы `cinemahall`; отдельно проверить возможность восстановления. Nginx/QuickShift не менять.
2. Получить протестированный коммит в `/opt/cinemahall-source`, установить backend зависимости `npm ci --omit=dev` из `backend/`.
3. Применить только `backend/migrations/005_catalog_identity_refresh.sql` к существующей базе `cinemahall`. Она аддитивная, повтор допускается, `title_id` сохраняет collation родительского ключа.
4. Запустить `node backend/backfill-catalog-identity.mjs` с теми же DB_* переменными, что API. Если возник `CATALOG_IDENTITY_CONFLICT`, миграцию данных откатит транзакция; выписать конкретные ID и разрешить конфликт вручную, не переназначать автоматически.
5. Проверить `node --check backend/server.mjs`, `node --check backend/sync-catalog.mjs` и запустить `npm test` на тестовой копии БД. Затем перезапустить только `cinemahall-api.service`.
6. Проверить `/health`, `/api/v2/config`, `/api/v2/home`, поиск русского и английского alias, скрытый и будущий релиз, сезоны/серии и 404/400. `/api/v1` должен продолжать работать. Проверить HTTP 200 существующего QuickShift.
7. Оценить нагрузку и квоты поставщика; после этого включить `CINEMA_REFRESH_ENABLED=1` в EnvironmentFile сервиса. Планировщик запускает не более одного worker, проход ограничен 100 due-записями, importer защищён advisory lock. Сроки обновления хранятся в MariaDB. При сбое запись остаётся due для следующего запуска; отдельной таблицы истории jobs пока нет.
8. Подключать TV после серверного resolver и теста на устройстве. Пока `serverPlaybackOptions: false`, переключение playback на сервер запрещено контрактом.

Если новая версия API не отвечает, вернуть предыдущий коммит сервиса без удаления таблиц миграции; новые таблицы не меняют существующий v1. Резервную копию сохранить до проверки чтения, истории и импорта.

## Серверный поиск источников, следующий шаг

После развёртывания API v2 можно отдельно задать `CINEMA_SOURCE_DISCOVERY=1` в защищённом EnvironmentFile сервиса и перезапустить только `cinemahall-api.service`. До включения `/api/v2/config` сообщает `sourceDiscovery: false`; TV продолжает свой прежний поиск. При включении TV-провайдер спрашивает сервер `/api/v2/titles/:id/source-candidates` и получает ограниченный список кандидатов; при недоступности сервера использует прежний путь. Перед включением проверить доступность поставщика с VPS, задержку и квоты на стороне сервера. Варианты раздач не сохраняются в БД; кэш памяти до 3 минут, не более 64 запросов. Выбранный источник по-прежнему открывается встроенным движком TV. Перенос транспортировки видео на VPS не входит в эту реализацию; он требует отдельного ресурсного теста и измерения сетевой нагрузки.

После успешной проверки v2 TV-провайдер автоматически использует сервер для рядов `movies` и `series`, поиска по ним, карточек и серий; локальный снимок остаётся резервным. Остальные шесть рядов пока читаются старым способом. Тесты на реальном TV должны подтвердить открытие серии и запуск выбранного источника после получения серверной карточки. Пока этот путь не проверен, распространять новую APK как окончательную сборку рано.

После миграции 005, backfill и проверки KinoAPI можно включить `CINEMA_REFRESH_ENABLED=1` в EnvironmentFile API. Планировщик раз в 30 минут проверяет таблицу `title_refresh_state` и запускает ограниченный проход `refresh 10`, когда есть due-записи. Состояние заданий хранится в БД; после перезапуска незавершённая запись остаётся due. Advisory lock не позволяет одновременно выполнять новый refresh и другой импорт. При отключённой переменной планировщик не работает. Отдельный systemd timer в этом режиме не нужен.
