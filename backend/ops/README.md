# Полное пересоздание CinemaHall API

`rebuild-api.sh --reset-cinemahall COMMIT_SHA [SNAPSHOT_DIRECTORY]` запускается от root на существующем VPS. Оператор явно разрешает удаление всей базы `cinemahall`, включая аккаунты, профили, историю, настройки и каталог. Настройки подключения и ключи берутся из `/etc/cinemahall/database.env`; нужны `DB_USER`, `DB_PASSWORD` и `KINOAPI_KEY`.

Сценарий извлекает полный backend и сборщик каталога через `git archive`, поэтому не зависит от sparse checkout. Новая версия находится в `/opt/cinemahall-api/releases/`, файлы каталога — в `/var/lib/cinemahall/`. Репозиторий `/opt/cinemahall-source` остаётся источником Git-объектов и резервным старым кодом.

До удаления рабочей базы создаётся защищённый SQL dump в `/root/cinemahall-rebuild-*` и проверяется его восстановление во временной базе. Затем временная база пересоздаётся с полной схемой и миграциями 002–005 (индекс 001 уже есть в `schema.sql`), наполняется свежим снимком, проверяется backfill и наличие фильмов, сериалов и эпизодов. Новая база содержит только новые данные; старые записи не переносятся.

После успешной подготовки заменяются только `cinemahall` и `cinemahall-api.service`. Сервис использует отдельную версию кода, слушает `127.0.0.1:8091`, включает серверный поиск кандидатов и refresh. `rebuild-runtime.env` фиксирует имя БД и эти флаги. nginx, сертификаты, системные пользователи, пароль MariaDB и другие приложения не пересоздаются. Новая API-версия сохраняет существующие v1 маршруты.

Если переключение или локальные HTTP-проверки завершаются ошибкой, обработчик восстанавливает прежний SQL dump и определение сервиса. Сценарий сохраняет резервные копии; при ошибке восстановления выводит `RECOVERY NEEDS ATTENTION`. Для проверки после успешного завершения нужны внешний HTTPS API и реальное воспроизведение на TV. Полноценная проверка systemd-переключения выполняется на VPS: локальная проверка shell не заменяет её.

Запускать через отдельный root `systemd-run` unit, чтобы закрытие SSH не прервало работу. При успехе журнал содержит `REBUILD_OK` с путями новой версии и резервной копии. При ошибке до переключения production база не пересоздаётся; временная база и диагностические файлы сохраняются.

Необязательный `SNAPSHOT_DIRECTORY` — существующий снимок из `/var/lib/cinemahall/rebuild-*`: его можно повторно импортировать после неудачной выкладки без загрузки с поставщика. Перед переключением сценарий запускает настоящий API на `127.0.0.1:18091` с временной базой и отключёнными планировщиками. Проверяются `/health`, `/config` и все восемь рядов `/home`. Ошибка этой проверки оставляет production базу действующей.

## Обновление кода после переустановки

`update-api.sh COMMIT_SHA` устанавливает новую версию backend без пересоздания базы и повторного импорта каталога. Проверяет отдельный процесс API на порту 18091, реальные байты постера через серверный image proxy и кандидатов источников контрольного сериала. Затем переключает только файл сервиса; при неуспешной проверке возвращает прежнее определение сервиса. Настройки и данные остаются действующими. В конце выводится `API_UPDATE_OK`. Этот сценарий предназначен для VPS, уже переустановленного `rebuild-api.sh`.

Image proxy использует фиксированные HTTPS-адреса `image.tmdb.org` и его CDN `tmdb-image-prod.b-cdn.net`. Проверка TLS остаётся включённой, перенаправления запрещены. После ошибки имени сертификата проблемный адрес пропускается на 5 минут, после других сетевых ошибок — на 15 секунд; успешный источник используется первым для следующих картинок.

На VPS оба имени разрешались в `127.0.0.1`, включая ответ Google DoH без специальных параметров. Проверка запроса с `edns_client_subnet=0.0.0.0/0` вернула публичный IP, а HTTPS-запрос к этому IP с исходным именем TMDB успешно загрузил JPEG. Поэтому загрузчик изображений использует [Google DoH](https://developers.google.com/speed/public-dns/docs/doh/json) с этим параметром, объединяет одновременные DNS-запросы и кэширует публичный IPv4 по TTL (не более 5 минут). Loopback, private и специальные адреса не допускаются. HTTPS `lookup` фиксирует выбранный IP, а Host, SNI и проверка сертификата сохраняют исходное имя. Глобальные `/etc/hosts` и настройки DNS не меняются. Перед переключением по-прежнему проверяются реальные байты постера.

У части публичных CDN-узлов на VPS также обнаружены таймауты подключения. После проверки байтов изображения успешный маршрут сохраняется отдельно в `/var/lib/cinemahall/image-cache/routes.json` (каталог принадлежит `cinemahall`, файл 0600). Это краткоживущая подсказка подключения до 24 часов, не изменение DNS: при каждом новом TLS-соединении проверяется исходное имя. Так тестовый и основной процессы используют один уже проверенный маршрут. Отказавший IP удаляется; следующая попытка выбирает свежий публичный адрес, в том числе через резервный DoH-запрос с фиксированной публичной подсетью `8.8.8.0/24`. Попытка соединения ограничена 2,5 секунды, общая загрузка картинки — 10 секундами. Обновлятор сохраняет проверенные маршруты в диагностическую копию и при ошибке после переключения печатает журнал основного сервиса перед откатом.

Для первого запуска после сетевого сбоя `update-api.sh COMMIT_SHA PUBLIC_IMAGE_ROUTE_HINTS` принимает до трёх публичных IPv4 через запятую. Они передаются только тестовому процессу как кандидаты подключения: сертификат и байты картинки проверяются обычным способом, и лишь после этого маршрут попадает в общий кэш. Это позволяет повторно проверить недавно работавшие адреса из диагностического журнала без жёсткого IP в коде приложения. При последующих запусках используется проверенный кэш и автоматический выбор адресов.
