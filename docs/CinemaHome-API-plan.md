# CinemaHome: потребности приложения, API, база и обновление

Дата: 28 октября 2026. Основа анализа: `main`, коммит `0b7106624c660c988ec2b64845f05485ed7092c4`, исходники Android TV, встроенного провайдера и backend; ограниченные публичные GET-проверки рабочего API. Это технический план и реестр требований. Предложенные маршруты, таблицы и интервалы ниже ещё не реализованы, если прямо не указано обратное. Внешние API и их квоты перед реализацией адаптеров нужно проверить по актуальной документации.

## 1. Что установлено

- Основная поддерживаемая платформа — Android TV. Mobile в README приостановлен; контракт проектируем переносимым, отдельный мобильный релиз не входит в ближайший этап.
- UI Nuvio работает через локальный провайдер `127.0.0.1:18991`, ID `app.cinemahall.catalog`. `CinemaCatalog` сначала читает snapshot, затем использует живой каталог. В проверенном дереве нет подключения этого провайдера к `cinemahome.duckdns.org`.
- `CinemaHallSourcePolicy` допускает собственный loopback-провайдер. Для перехода на сервер его не нужно отключать: сервер подключается внутри нашего провайдера, UI продолжает получать совместимый ответ.
- Рабочий `/health` сообщает подключённую БД. `/api/v1/catalog-stats` в момент проверки: 405 фильмов, 305 сериалов, всего 710; у 41 записи нет постера, у 22 нет описания. Это наличие полей, а не проверка качества или доступности изображений.
- На главной обнаружены будущие релизы 2028–2043 годов, а также японские названия. Выборка по `updated_at` отражает порядок изменения базы, а не популярность, новизну релиза или возможность просмотра. Неизвестная дата не должна автоматически считаться состоявшимся релизом.
- `Fight Club` вернул 0 результатов, `Бойцовский` — 1. Карточка этого же фильма содержит alias `Fight Club`: проблема в поиске, а не в отсутствии записи.
- `discover?yearFrom=abc` вернул 200 и обычную выдачу: некорректный фильтр молча игнорируется.
- В `discovery.mjs` до локальных правок каждый discover читал `kind,year,payload` всей таблицы ради справочников, даже если справочники не запрашивали.
- `sync-catalog.mjs` уже имеет MariaDB advisory lock, нормализацию, повтор запросов, три режима bootstrap/daily/one, частичное сохранение кураторских правок. Это заготовки, их следует развивать.
- Daily обходит первые страницы по популярности и latest. Сохранённые непопулярные сериалы не получают гарантированного повторного обхода. Записи со статусом completed пропускаются без ограничения по давности; их описания, изображения и рейтинги могут устаревать навсегда.
- В проверенном sync нет заполнения таблицы episodes; импорт snapshot умеет импортировать серии. Наличие карточки сериала не гарантирует полноту сезонов.
- Планировщик живёт в процессе API, зависит от admin-секретов и отмечает дату запуска при старте дочернего процесса, до подтверждения успеха. Нужны постоянные задания, результат выполнения и восстановление после сбоя.
- Уже есть account/profile/sync API и слой совместимости `/auth/v1`, `/rest/v1/rpc`. В TV настройки сторонних аккаунтов и интеграций скрыты. Наличие серверных маршрутов не доказывает завершённую синхронизацию собственного приложения.

## 2. Какую систему собираем

Один серверный каталог — источник истины для метаданных, подбора контента и правил публикации. Android TV получает эти данные через собственный provider-adapter; локально остаются интерфейс, плеер, работа с устройством, кэш и воспроизведение через встроенный движок. Существующий VPS предназначен для метаданных и небольших фоновых задач. Перенос видео и тяжёлого torrent engine на него не предполагается.

Три независимых понятия: `metadataState` (насколько заполнена карточка), `publicationState` (можно ли показывать), `availability` (что известно о воспроизведении). Запись в каталоге, состоявшаяся премьера и доступный проверенный источник — разные факты. Допустимые состояния источников: `unknown`, `checking`, `available`, `unavailable`, `stale`; у всех есть время проверки. Только фактическая проверка потока даёт verified media capabilities.

Приоритеты: P0 — условие корректного базового сценария; P1 — полноценный удобный продукт; P2 — расширение. «Частично» означает, что в коде есть часть механизма, но не подтверждён весь путь сервер → TV → воспроизведение. Наличие upstream-экрана не считается готовой функцией CinemaHome.

## 4. Целевой API: границы и маршруты

Это проект контракта. Действующие `/health`, `/api/v1/home`, `/search`, `/titles/:id`, `/titles/:id/seasons`, `/genres`, `/filters`, `/discover`, `/catalog-stats` сохраняются на переходный период. Account/RPC-совместимость не переписываем одновременно с каталогом. Несовместимые изменения формы ответов вводим как `/api/v2`, не ломая существующий `/api/v1`.

### Обязательные DTO

- **TitleCard**: id, type (`movie|series`), title, originalTitle?, year?, poster?, backdrop?, ratings[], ageRating?, releaseState, availability, version. Без cast, всех aliases и эпизодов. Nullable поля действительно null, UI знает placeholder.
- **TitleDetail**: поля карточки + titlesByLanguage, aliases, description, descriptionLanguage, releaseDates[], runtimeMinutes?, genres[], countries[], languages[], externalIds, cast[], crew[], trailers[], images, seasonsSummary?, metadataState, updatedAt. Full provenance — в admin, публично только безопасные источники и свежесть.
- **Image**: url, role, width?, height?, language?, verifiedAt?. Original URL можно хранить, TV получает подходящий размер. Доступность картинок проверяется выборочно и по очереди, не всеми при каждом запросе.
- **Rating**: source, value, scale, votes?, fetchedAt. Значение без числа голосов не используется для топа с порогом votes.
- **SeasonSummary**: id, titleId, number, name?, poster?, episodeCount?, airedEpisodeCount?, nextAirAt?. Номер 0 допустим для specials.
- **Episode**: id, titleId, seasonId, season, number, absoluteNumber?, title?, description?, still?, airAt?, runtimeMinutes?, releaseState, availability, version.
- **Availability**: status, checkedAt?, expiresAt?, reasonCode?. `available` не означает, что на любом TV гарантирован HDR/DV.
- **PlaybackOptions**: titleId/episodeId, strategy (`local|remote`), resolverVersion, matchIdentity, preferredQuality?, preferredVoice?, options?, checkedAt?, expiresAt?. Для local клиент использует свой движок. Если сервер ещё не проверял варианты, options не выдумывает.
- **PlaybackOption** (если сервер реально знает): id, quality, voice {id,label,language}, claimedCapabilities, verifiedCapabilities?, availability, sourceCount. Сырые credential headers и постоянные playback URL не входят в общую карточку.
- **Page**: items, nextCursor|null, catalogVersion. Cursor содержит сортировку, last sort key, last ID и fingerprint фильтров; смена фильтра со старым cursor → 400. Для изменяющихся подборок фиксируем generation подборки, чтобы не пропускать/повторять элементы при изменении рейтинга.
- **Error**: code, message, retryable, requestId, retryAfterSeconds?. 404 unknown title отдельно от 503 provider temporarily unavailable.

Пример локальной стратегии: сервер возвращает canonical title ID, корректные external IDs, названия для сопоставления, год, season/episode и ограничения выбора. Встроенный provider на TV получает кандидатов и превращает результат в существующий `StreamResponseDto`. Сервер не отдаёт ложный `url` только ради заполнения поля.

## 5. Модель БД и миграция

| Сущность | Что хранит | Ключевые ограничения |
|---|---|---|
| titles | Внутренняя карточка, статусы, version, даты | Неизменяемый internal ID; legacy ID остаётся alias |
| external_ids | provider + entityType + externalId → internal ID | Unique(provider, entityType, externalId) |
| title_names | Язык, роль названия, normalizedName | Индекс поиска; дубль не создаёт второй фильм |
| genres / countries / title_taxonomy | Нормализованные справочники и связи | Unique canonical code и пары связи |
| images | Роль, URL, размер, язык, provenance | Постер и фон отдельно |
| ratings | Источник, значение, scale, votes, fetchedAt | Unique(titleId, source) |
| people / credits | Персоны, роль, character, порядок | Устойчивые ID персон |
| seasons / episodes | Порядок и метаданные серий | Unique(titleId, seasonNumber), Unique(seasonId, episodeNumber) для выбранного canonical порядка |
| episode_mappings | Нумерация внешних провайдеров | Mapping к canonical episode ID |
| metadata_sources | Origin, freshness, conflict, raw checksum | Bounded raw payload retention |
| collections / collection_items | Редакторские подборки и порядок | Стабильные IDs, атомарная публикация generation |
| catalog_redirects / catalog_changes | Слияния, удаления, версии | Старые ссылки разрешаются, cursor монотонен |
| ingestion_jobs / ingestion_tasks | Очередь, checkpoint, lease, retry | Unique active dedupe key; leaseExpiresAt индекс |
| refresh_state | lastSuccess, nextRefreshAt, failures | Выборка due по nextRefreshAt, priority |
| moderation / overrides | Политика публикации, ручные правки | Импорт не перезаписывает locked fields |
| source_cache | Кратковременные результаты resolver | TTL; без видео и torrent payloads |
| Существующие accounts/profiles/sync_* | История, библиотека, настройки | Привязка к canonical ID через migration mapping |

Не превращать существующий JSON payload сразу в десятки обязательных JOIN. Первый шаг: external_ids, title_names, refresh_state, persistent jobs, публикация; затем нормализовать эпизоды и часто используемые фильтры. JSON оставить для исходных данных и редких дополнений. Индексы выбирать по реальным запросам и EXPLAIN.

Миграция: backup → создать новые таблицы → backfill с проверкой конфликтов → заполнить ID mapping → сравнить старые/новые DTO на тестовых произведениях → включить v2 в адаптере для части запросов → наблюдать → переключить. Не пересоздавать все IDs и не очищать историю. Destructive cleanup отдельно от импорта, с отчётом точных записей и возможностью восстановления.

## 6. Наполнение каталога

1. **Инвентаризация:** распределение по типу, языку, статусу, источникам; доля постеров/фонов/описаний; сериалы без серий; дубли и анонсы в доступных рядах. Начальные 710 записей — не целевой лимит.
2. **Единая нормализация:** snapshot importer и live sync используют одинаковую модель IDs, enum, названий, дат, изображений и content policy. Предупреждения записываются в job report.
3. **Первичное покрытие:** ограниченные страницы популярных, топовых и свежих релизов по фильмам/сериалам. Отдельно пополнять классику и менее популярные произведения, не оценивать полноту количеством первых страниц.
4. **Полные карточки:** списки поставщика могут быть сокращёнными; детали дозагружаются отдельными задачами. Из них заполняются cast, crew, ratings, изображения, сезоны и серии.
5. **Обогащение:** предпочтение проверенному русскому названию и описанию; альтернативные источники подключать адаптерами с квотами, схемами и метриками. Не выдумывать недостающие даты, длительность, переводы и изображения.
6. **Правила слияния:** ручная правка → подтверждённое значение профильного источника → основное значение → fallback. Пустой новый ответ не стирает старое. Смена рейтинга не поднимает старый фильм в ряд новых релизов.
7. **Публикация:** `draft → ready → published`; проблемы классификации → `review`, скрытие → `hidden`. Анонсы могут жить в отдельном planned-разделе, не становясь доступными для просмотра автоматически.
8. **Проверка качества:** hero требует нормальное название, широкое изображение и описание; обычный ряд — название, тип и постер либо явно допускаемую заглушку. Все карточки доступны по ID даже при ограничении публикации, если это не нарушает content policy, с понятным состоянием.
9. **Контентная политика:** в текущем коде уже есть anime exclusion/review, но он непоследователен между импортами. Вынести это в общую конфигурацию и классификатор. Ничего не удалять по японскому языку или по принадлежности к анимации; спорные случаи скрывать/помещать на review согласно выбранной политике. Обновление не возвращает ранее скрытые записи без разрешённого перехода состояния.

## 7. Логика обновления

Стартовые интервалы ниже — проектные значения, их корректировать по квотам источника и измерениям. Они не настроены на рабочем сервере этой работой.

| Очередь | Когда и как часто | Что делает |
|---|---|---|
| discovery-new | Каждые 6 часов с ограничением страниц | Ищет новые записи, сохраняет checkpoint |
| series-airing | Каждые 6 часов; около ожидаемого выхода — 1–2 часа в пределах budget | Обновляет сезон, даты, новые серии и доступность metadata |
| series-ongoing | Раз в сутки | Повторный обход известных незавершённых сериалов |
| upcoming | Раз в сутки ближе к релизу; раз в неделю для далёких дат | Уточняет премьеру и статус |
| recent-released | Раз в сутки первые 30 дней | Описание, artwork, рейтинги, релизный статус |
| completed | Раз в 30 дней, с jitter | Исправления метаданных; не пропускать навсегда |
| ratings-popular | Раз в сутки для популярных, раз в неделю для остальных | Рейтинги и votes без изменения release ordering |
| repair-missing | Низкий приоритет, ограниченная пачка ежедневно | Отсутствующие постеры, переводы, серии, данные персон |
| user-open stale title | Возвращает last-good сразу, ставит refresh в очередь | Никакого ожидания нескольких внешних API внутри GET |
| availability/source cache | На TV по запросу; стартовый positive TTL 15–60 мин, negative 2–5 мин | Не гонять весь каталог через resolver |
| maintenance | Небольшими пачками ежедневно | Expired cache, старые job details; не удаляет библиотеку |

Каждая задача: `queued → leased → running → succeeded / retry_wait / failed`. Поля: jobId, dedupeKey, priority, entityId, provider, attempt, nextAttemptAt, leaseUntil, checkpoint, createdAt, startedAt, finishedAt, lastErrorCode, counters. Parent job успешен только после завершения его задач; частичный успех явно partial. Retry исчерпан → dead-letter/review, а не бесконечный цикл.

Один worker на старте, одна внешняя операция одновременно, rate budget по поставщику, CPU/память измерить. При 429 учитывать Retry-After; transient 5xx/timeout повторять с exponential backoff+jitter; invalid key 401/403 останавливает очередь поставщика и выводит admin-сообщение. Восстанавливать просроченные leases при старте. Отдельный scheduler создаёт due tasks, worker выполняет; admin только управляет, API обслуживает чтение.

Перед записью сравнивать checksum нормализованных полей: неизменившийся объект обновляет `lastCheckedAt`, но не `catalogVersion` и не ряд Новинки. Изменение карточки и catalog_changes писать одной транзакцией. Events для клиента публиковать только после commit. Массовая пересборка подборок получает новую generation и переключается атомарно.

Первый вертикальный срез: Home → поиск «Fight Club» → карточка «Бойцовский клуб» → local options → play → progress → resume. Второй: сериал с несколькими сезонами → конкретная серия → завершение → следующая серия → обновление расписания. Это проверяет полезность API до массового расширения базы.

### Приёмка и целевые метрики

- 100% fixture ID сохраняются между snapshot, API, provider и историей; redirect не теряет progress.
- Поиск русского и английского alias возвращает один canonical фильм; описания не создают ложных совпадений.
- Invalid filters дают 400, unknown title 404, отказ БД 503; серверная ошибка не очищает TV cache.
- Пагинация корректна на 0, 1, ровно limit и limit+1 записях, а также при равных сортируемых значениях.
- Импорт одного набора дважды не плодит записи; пустые поля и смена поставщика не теряют overrides.
- Перезапуск во время импорта продолжает работу; ошибка worker не считается успешным обновлением дня.
- Серии сохраняют нумерацию и ID; future/unknown episode не выдаётся за доступную автоматически.
- Метрики покрытия выводят numerator/denominator; предварительная цель для опубликованных основных рядов — 100% обязательных полей. У всего архива цель отдельно, не подгонять её удалением проблемных записей.
- Начальные performance budgets для проверки: тёплые home/search/detail p95 ≤500 мс на сервере, home JSON ≤250 КБ, page ≤60 карточек. Это проектные цели, не измеренные результаты. Playback start измеряется отдельно на TV и сети пользователя.
- Перед production: migrations на копии БД, restore test, MariaDB integration tests, Android build, реальные D-pad/playback тесты. Ни один из них не заменяется моками.

## 9. Что сделано в этой рабочей копии

После выявления проблем подготовлен небольшой независимый патч `/api/v1`, без выкладки на VPS:

- Поиск использует titleRu/titleEn/originalTitle/aliases наряду с title; значения связаны параметрами, LIKE wildcard экранируются явно.
- Discover не читает весь payload каталога ради ненужной агрегации фильтров.
- NaN/Infinity и обратный диапазон годов отклоняются до запроса к БД.
- Сортировка имеет tie-break ID; lookahead отличает полную последнюю страницу от наличия следующей.
- Добавлены 8 backend unit/contract tests; вместе с 3 существующими web catalog tests проходят 11 тестов. Они используют mock query и не подтверждают исполнение JSON_SEARCH на рабочей MariaDB, производительность, Android build или TV playback. SQL и коллацию необходимо проверить интеграционно перед выкладкой.

Рабочий сервер и база этой работой не менялись. Приложение не переключено на новый источник. Этот документ — база для следующих реализационных этапов; полный реестр не объявляется реализованным.

## Текущий этап реализации, 28 октября

Цель уточнена: сервер выполняет каталогизацию, обновление, поиск, построение рядов, сопоставление произведений и в конечной архитектуре подготовку источников для воспроизведения. TV получает готовые небольшие ответы и выполняет только интерфейс и воспроизведение. Мобильное приложение и веб — последующие этапы.

В ветке добавлены API v2 для главной, поиска, карточек, сезонов и эпизодов; безопасная выдача без полного payload; небольшие изображения TMDB; миграция таблиц внешних ID и сроков обновления; backfill с остановкой на конфликтах; отдельный режим refresh уже известных записей. Текущий playback-options возвращает `strategy: local`, а config явно сообщает `serverPlaybackOptions: false`: **перенос поиска и подготовки источников на сервер ещё не готов**. Перед переключением TV нужны серверный resolver, проверка качества вариантов и измерение ресурсов VPS. Статусы этих возможностей нельзя выдавать за завершённые.

На изолированной MariaDB 10.11 и в HTTP-интеграции пройдены 24 теста; они не доказывают работу на реальном Android TV. API v2 и миграция ещё не развернуты на VPS. Рабочий API v1 остаётся действующим.

Следующее изменение чернового PR: добавлен серверный поиск вариантов воспроизведения с ограничениями по запросу, времени и кэшу. Провайдер TV использует его при `sourceDiscovery: true`, затем прежний локальный поиск при недоступности сервера. Это переносит поиск и первичный отбор источников на VPS, но подготовка потока и декодирование пока выполняются на TV. Для полного «тонкого клиента» потребуется вынести подготовку потока, проверить ресурсы VPS и испытать поведение на телевизоре; отдельная мобильная и веб-реализация откладывается.

Адаптер Android TV теперь читает два базовых ряда, их поиск, карточки и эпизоды из API v2 через существующий loopback-провайдер. Для остальных рядов и при ошибке API остаётся существующий снимок/старый путь. Карточки, выданные сервером, преобразуются в действующий Nuvio contract, а документ для воспроизведения берёт те же canonical ID и внешние ID. Это работающий код перехода, но Android APK и реальное воспроизведение ещё должны пройти CI и проверку на устройстве.
